# 《电商运营助手》面试内容整理

> 覆盖笔记 01–14 全部内容。面试向速记，答案采用「要点式」而非成段叙述，方便临场展开。

---

## 一、项目速览

**一句话定位**：面向电商运营人员，用「多 Agent + 大模型」自动完成运营工作流的平台（商品诊断 → 主图/视频方案 → 媒体素材生成 → 库存建议 → 经营复盘 → 投放建议），全程带人工审批与可靠执行保障。

**贯穿案例**：便携装每日坚果 25g×30 袋，售价 39.9 元 / 成本 22.5 元，目标人群通勤上班族。

**技术栈**：

| 层 | 技术 |
|---|---|
| 前端 | Next.js 16（App Router）+ React 19 + TypeScript + Tailwind v4 + react-hook-form/zod + echarts |
| 后端 | FastAPI + Pydantic + SQLAlchemy 2.0 + Alembic |
| 任务 | Celery + Redis（broker/backend） |
| AI 编排 | LangGraph（StateGraph + checkpoint） |
| 大模型 | OpenAI 兼容协议（文本）+ 火山引擎即梦（文生图 3.0 / 文生视频 3.0） |
| 存储 | MySQL（业务事实）、Redis（消息队列）、PostgreSQL（LangGraph checkpoint） |
| 可观测 | OpenTelemetry |

## 二、架构与模块地图

```
React 前端（App Router）
        │ REST
FastAPI（schemas / services / routes / main）
        │
  ┌─────┴──────────┬──────────────┬─────────────┐
  业务服务层        Agent 编排层     任务层        AI 能力层
  (products等)     (LangGraph图)   (Celery)     (llm/媒体生成)
        │              │              │             │
  ┌─────┴──────────────┴──────────────┴─────────────┐
  MySQL(业务)  Redis(队列)  PostgreSQL(checkpoint)
```

**核心数量**：7 条工作流、9 个 Agent、16 个工具（风险分级 R0–R3）。

**三库分工**（高频考点）：
- MySQL —— 业务事实（商品、方案、素材、任务、审批）
- Redis —— Celery 消息队列与结果存储
- PostgreSQL —— LangGraph checkpoint（技术恢复，不存业务事实）

## 三、面试问题分类整理

### 3.1 项目整体与架构设计

**Q：为什么不用"一个 LLM 大模型写到底"？**
- 幻觉、无真实数据/工具，不可控、不可审计
- 采用职责分离的多 Agent：协调 Agent 与质量合规 Agent **零工具**，实现「编排与执行分离、生成与审查分离」
- 工具白名单 + 风险分级 R0（只读）/R1（草稿）/R2（执行）/R3（高危）
- R2/R3 副作用必须过人工闸门（`human_review_gate` + `interrupt()`），先草稿后落库

**Q：Harness 工程是什么？**
- **不是可安装框架，是一组工程约束集合**，回答"在什么范围内做"
- 四维度：可控 / 可恢复 / 可验证 / 可观测
- 十个落点：合同、节点声明、版本化注册表、策略、脱敏预算、工具网关、租约、事件、审批、检查点维护
- Agent 管"做什么"，Harness 管"允许在什么边界内做"

**Q：为什么用两个关系型库（MySQL + PostgreSQL）而不是一个？**
- 按职责分离：MySQL 存业务事实，PostgreSQL 存 LangGraph 的可恢复状态
- checkpoint 若用 MemorySaver，进程重启即丢、无法多进程读取；PostgreSQL 持久化、可共享

**Q：项目分层结构？**
- `schemas.py`（Pydantic 数据合同）/ `services/`（业务）/ `routes/`（路由）/ `main.py`（注册挂载）
- 前端隐藏按钮不算安全边界，后端必须独立校验

### 3.2 认证与安全

**Q：认证怎么实现？为什么不引第三方 JWT？**
- 自实现 HMAC Token：`载荷.签名` + base64url
- 密码用 `pbkdf2_hmac(sha256, salt, 120_000)` + 随机盐，`hmac.compare_digest` 常量时间比较（防时序侧信道）
- 轻量、可替换；每次请求**回查用户状态**，实现「停用即失效」（用性能换实时性）
- Token 只放 `sub/email/role/exp`

**Q：认证 vs 授权的边界？**
- 认证：你是谁（Token 有效性）
- 授权：你能做什么（角色 `owner/operator/viewer` → 派生权限 → `require_edit_permission` 等 FastAPI 依赖）
- 状态码：401（未认证/Token 无效）、403（权限不足）、422（数据合同校验失败）

**Q：密钥如何防泄露？**
- `.env`（真密钥，不提交）与 `.env.example`（占位符，提交）分离
- 密钥只放服务端、只进请求头，异常不回显原文
- 接口只返回 `api_key_masked` + `has_api_key`
- 日志脱敏：`redact_snapshot` 三重上界（深度 8、条目 200、字符串 2000）

### 3.3 数据模型与数据库

**Q：Task 与 Run 为什么分离？**
- **Task（业务目标）** 给人看，**Run（执行实例）** 给机器看
- MySQL 存业务事实，checkpoint 只管技术恢复，两者不能互替
- 状态机：`queued → running → awaiting_approval → completed`

**Q：聚合根级联设计？**
- `Product` 作为聚合根，`cascade="all, delete-orphan"` 级联所有运营子实体
- 与 `ondelete="SET NULL"`（如 agent_run 删除后诊断保留）的区别要分清
- 多外键关系需 `foreign_keys=` 消歧

**Q：库存怎么防超卖/重复扣减？**
- `InventoryItem` 存快照 + `InventoryMovement` 存 before/after 流水
- `movement_type` 区分 `LOCK/RELEASE` 与真实增减
- 库存走流水回溯而非直接改数量，超量拒绝

**Q：多租户隔离怎么做？**
- 靠 `workspace_id` 贯穿
- 校验发生在写库之前（`_validate_context_scope`），不是写后补救
- 路径工作区与认证工作区必须一致（不一致 403）

**Q：金额精度？**
- `Numeric(10,2)` + `Decimal`，避免浮点误差

### 3.4 大模型接入工程化

**Q：模型配置来源与优先级？**
- `.env` 做启动兜底，**数据库做运行期权威配置**（`PATCH /model-settings`）
- 非空字段覆盖：避免只改一个字段时清空其余字段
- DB 不可用回退 env

**Q：如何保证 LLM 输出稳定符合 schema？**
- 三层防线：`response_format={"type":"json_object"}` + 提示词示例 + Pydantic `model_validate` 强校验
- 统一封装 `create_json_chat_completion()`：拼接 `/chat/completions`、httpx、Bearer、`raise_for_status`、解析 `choices[0].message.content` 并处理「两层 JSON」（外层厂商协议 + 内层业务数据）

**Q：为什么不引入第三方 OpenAI SDK 而自写 httpx 调用？**
- 只要 OpenAI 兼容协议，自写更可控、更轻
- 统一处理超时、错误分类（`LLMNotConfiguredError→400`、`LLMResponseError→502`）

**Q：模型输出不稳定时的容错策略？**
- **规则兜底（`source="rules"`）**：LLM 失败回退规则，保证链路不断，但不伪造数据
- `raw_output.fallback_reason` 说明失败原因
- `source` 标记来源，避免「规则版冒充 AI」
- 文本三项无默认值 = 明确「未配置」，而非给错误默认值

**Q：Prompt 注入防护？**
- system 固定边界（只输出 JSON），user 放业务材料，用户资料视为不可信
- 上下文最小化：只喂商品/竞品/诊断/素材/经营记录，不含密钥账号

**Q：上下文长度与成本控制？**
- 竞品截断、只取近 5 期经营记录
- 预算「调用前截断」而非事后统计：`remaining_model_tokens` 返回 `min(申请, 剩余)`，归零熔断

### 3.5 媒体生成服务（08）

**Q：媒体生成与文本生成的本质区别？**
- 媒体是**异步 + 消耗外部额度的一次性动作**，失败不能伪造图片、没有「规则版图片」兜底
- 三大保证：①先校验再花钱 ②中间状态可查询（task_id）③结果必须落地（本地路径）

**Q：单次生成流程（九步）？**
- 配置守卫 → 类型守卫 → 取提示词（缺失时拼接兜底）→ 清洗 → 签名提交 → 轮询 → 提取 URL → 下载落地 → 返回素材字典
- **前五步任何一步失败都不会产生素材记录**

**Q：火山引擎签名怎么做（HMAC 派生链）？**
- 第一轮 HMAC 直接使用**原始 Secret Key**
- 依次派生：日期 → 区域(`cn-north-1`) → 服务(`cv`) → request
- 四类标识要分清：本地任务 ID、供应商 `task_id`、临时 URL、本地路径

**Q：为什么素材记录存本地路径而不是供应商 URL？**
- 供应商 URL 有时效（视频约 1 小时），会过期
- 本地路径稳定，审核记录、投放实验、经营复盘都能继续引用

**Q：清洗函数的作用边界？**
- `_sanitize_*` 只清理协议不接受的特殊字符（¥、弯引号、U+2028/2029），**不是内容安全/版权/合规审核**
- 下载成功默认「待评估」，能否投放由人判断

**Q：视频生成的特殊限制？**
- 只支持文生视频（`jimeng_t2v_v30`），带参考图直接拒绝
- 时长换算帧数 `24×秒数+1`，仅 5s（121 帧）/10s（241 帧）
- 多一层 `workflow` 元数据（文生/图生、字幕、配音、剪辑说明）

### 3.6 后台任务与可靠执行（09）

**Q：为什么耗时生成必须任务化？**
- 同步调用会遇到：网关超时结果无人接收、无法知道失败在哪步、偶发失败即丢失、无法中止、重复生成
- 任务化：接口立即返回 `202`，后台执行；数据库保存状态/尝试次数/错误摘要/事件流；退避重试；取消接口；行锁防重复

**Q：任务状态机？**
- `pending → running → succeeded`
- `running → pending`（未达上限自动重试）/ `running → failed`（达上限）
- `pending/running → cancelled`（取消）
- `failed → pending`（人工重试，`attempts` 不清零）
- 三条规则：running 只能由 pending 进入；failed/cancelled 是终态；pending 来自三个方向

**Q：如何保证重复消息只执行一次？**
- `run_generation_job()` 用 `db.get(..., with_for_update=True)` 行锁 + 只处理 `pending` 状态检查
- 三道防重复不冗余：租约防并发重复、幂等键防重放重复、检查点恢复防重跑重复

**Q：inline 与 Celery 的选择？**
| 对比 | inline | Celery |
|---|---|---|
| 执行位置 | API 进程内后台任务 | 独立 Worker |
| 依赖 | 无 | Redis + Worker |
| 重启恢复 | 不自动恢复 | 队列仍在，Worker 继续消费 |
| 适合 | 本地开发/轻量演示 | 接近生产 |

- 两者复用同一条 `run_generation_job()`

**Q：`202` 代表什么？**
- **只表示任务已落库并开始调度，不等于成功**，结果要看任务状态
- 事务提交必须先于分发（`commit()` 在 `dispatch()` 之前），否则后台读不到记录

**Q：重试退避策略？**
- 第 `attempts` 次失败后等待 `attempts × 2` 分钟，最长 10 分钟
- `max_attempts=3` 是「最多三次尝试，包含第一次执行」

**Q：取消的语义？**
- 取消是**本地状态操作**，不保证中止供应商已受理的请求，也不撤回费用
- 只有 `pending/running` 可取消，终态不可回滚

### 3.7 多 Agent 编排（LangGraph / Harness）

**Q：为什么用图编排而不是 if/else 写死？**
- LangGraph `StateGraph`：节点只返回增量字段，`add_edge`/`add_conditional_edges` 固话执行顺序
- 天然支持 `interrupt()` 暂停 + `Command(resume=...)` + 同一 `thread_id` 恢复（人审场景）
- 平台图通过注册表动态装配，加业务线「零编排成本」

**Q：interrupt() 前为什么不能产生副作用？**
- 恢复时 checkpoint 会重新执行该节点，副作用会重复执行
- 暂停点设计在「质量检查后、采用前」，未通过人工审批前不落库

**Q：两张图（基础图 vs 平台图）为何并存？**
- 基础图 7 节点（含返修回路、人审中断），平台图 5 固定节点 + 循环注册 `workflow.agents`
- 平台图跳过 `quality_compliance_agent` 注册（质量门由规则实现）

**Q：返修环如何防无限循环？**
- `prepare_revision → diagnosis` 返修环用 `max_revisions` 限次
- 达到上限仍交人工 ≠ 自动通过

**Q：依赖注入插座？**
- `AgentWorkflowDependencies` / `PlatformWorkflowDependencies`，图不碰 DB/运行器，便于测试（`InMemorySaver` + `FakeCompletionClient`）

**Q：Agent 与模型的关系？**
- **Agent ≠ 模型**：商品策略和创意策略可共用同一模型，差异在输入/提示词/输出结构
- 读上下文、质量检查不调模型
- 确定性优先于智能：意图路由用关键词、质量门用规则、模型失败用规则兜底

### 3.8 数据契约与工具边界（11）

**Q：数据合同是什么？**
- **节点间内存数据形状**，不是数据库表、不是接口 request/response（不做 Alembic 迁移）
- `StrictModel` 用 `extra="forbid"` 关闭 Pydantic 字段宽容，防 LLM 输出漂移
- 关键字段 `min_length=1` 挡「空字符串结论」；`creative_plans` 用 `min_length=3, max_length=6` 把业务规则写进数据形状

**Q：为什么共享状态选 TypedDict 而非 Pydantic？**
- `AgentWorkflowState` 用 `TypedDict(total=False)` 描述共享状态键集合，本身不做校验
- 代价：无校验；补偿：关键数据必须先过 Pydantic 模型

**Q：工具白名单如何实现最小权限？**
- `AGENT_TOOL_ALLOWLIST` 用 `frozenset`；`require_tool_permission` 用 `get(agent_name, frozenset())`——未知环节取空集必然抛错，宁可拒绝不静默放行
- 诊断/创意拿不到读工具，只有 `finalize_output` 持有写工具——**模型从头到尾没有直接读写业务通路**

**Q：脱敏为什么按键名而非扫描值？**
- `redact_snapshot` 匹配**字段名**正则，不是字段值
- 局限：`{"message":"api_key=sk-xxx"}` 不会被脱敏；脱敏也不是访问控制
- `Sequence` 判断后必须排除 `str/bytes/bytearray`，否则字符串被逐字符递归

**Q：跨字段组合校验？**
- 单个字段合法 ≠ 组合合法
- `ReviewResumePayload` 用 `model_validator(mode="after")` 校验 `edit_and_approve` 必须带 `edited_output`

### 3.9 工具网关与人工审批（13）

**Q：工具网关的固定执行顺序？**
- `execute()` 单一入口：租约 → 工作区 → 角色 → `authorize_tool` 策略 → 幂等 → 执行 → 脱敏落库
- 7 项适配表，未适配明确拒绝
- 幂等键 `tool:{agent_key}:{tool_key}`

**Q：风险分级 R0–R3？**
- R0 只读 / R1 草稿 / R2 执行 / R3 高危（如 `inventory.adjust`，仅 owner）
- `allowed=True` ≠ 不需要审批：R2/R3 会 `allowed=True, requires_approval=True`

**Q：五道授权判断为什么前三个抛异常、后两个返回值？**
- 前三道（未注册/白名单外/配置错误）抛异常 → 配置问题
- 后两道（只读成员/所有者限制）返回 `allowed=False` → 正常业务结果
- 全工程只有一个 `AgentPolicyError`，`except` 一定能捕获

**Q：source 与 provenance 的区别？**
- `source` 答「谁写的」（`llm`/`rules`）
- `provenance` 答「为什么」（如 `fallback_reason`）
- 规则兜底保证「模型不可用 ≠ 流程中断」

**Q：质量门怎么打分？**
- `BANNED_CLAIMS` 黑名单 + 5 类 `QualityIssue`
- `score = 100 - 20×error - 5×warning`

### 3.10 分布式可靠性与可观测性（12/14）

**Q：Transactional Outbox 为什么必须同事务？**
- 跨进程通知必须延迟到事务提交后，否则回滚/崩溃时会「消息发了但业务没落库」或「业务落库了但消息丢了」
- `create_agent_task` 建任务 `flush` + 建运行 `flush` + 写 `queued` 事件 + 建 `OutboxEvent`，**创建函数不提交事务，提交留给调用方**（要么都在要么都不在）
- 幂等键 `agent-run:{run_id}:{suffix}`，`suffix` 为 `start` 或 `approval-{id}`

**Q：Outbox 如何投递？**
- `dispatch_pending_outbox_events` 用 `with_for_update(skip_locked=True)` 扫描（防多实例抢同一条）
- 失败指数退避 `2^attempts`（封顶 300s），≥10 次标 FAILED
- 双保险：周期 Beat 扫描 + `kick_outbox_dispatcher` 即时触发（Redis 瞬时故障不误判失败）

**Q：租约（lease）与 fencing 如何阻止旧 Worker 写终态？**
- 认领：`_claim_agent_run` 用行锁做状态 CAS（`QUEUED/RESUME_QUEUED → RUNNING`），写 `lease_owner` + `lease_expires_at`
- `require_active_lease()` 五道拒绝：不存在/非 RUNNING/易主/取消/超时 + `with_for_update` 行锁
- fencing：`_sync` 在 completed/rejected 分支断言状态必须已被 fenced finalize 提交，否则抛 `AgentLeaseLostError`

**Q：恢复 / 重试 / 超时 三者语义？**
- **恢复（re-queue）**：租约过期 → `attempt+1` 重入队列，写 recovery Outbox（幂等键含 attempt）
- **重试（Celery retry）**：任务异常 → Celery 层重试
- **超时（FAILED）**：运行超时 → 直接失败，停止重试
- 取消优先、超时停重试、租约过期重新排队

**Q：`task_acks_late` 为什么安全？**
- 执行成功后再确认消息；Worker 崩溃消息被重新投递
- 重复投递被 DB 幂等 + fencing 吸收，不会重复执行

**Q：三类运行态维护？**
- `maintain_agent_runtime` 每 30s 扫描 RUNNING：取消 → CANCELLED、超时 → FAILED、租约过期 → 重入队列
- 审批过期 → EXPIRED（持久化终态，返回 409，不随响应回滚）
- 记忆过期 → EXPIRED

## 四、易混淆概念速查表

| 易混淆 | 澄清 |
|---|---|
| Agent / Workflow / Tool | Agent=决策角色，Workflow=业务编排线，Tool=原子操作 |
| 任务 ID vs 供应商 task_id | 两套编号体系，查询用本地 ID |
| `source=llm` vs `rules` | 来源标记，防止规则版冒充 AI |
| `image_prompt/video_prompt` | 只是文字，不出图/视频 |
| 接口带 `generate` | 不一定是 AI（推广链接、实验草稿是规则） |
| 数据表存在 ≠ 功能已接入 | 路由占位返回 501 未替换 |
| `202` vs `200` | 202=已入队调度，不等于成功 |
| `queued` vs `pending` | queued 是事件名，pending 是状态值 |
| `retry_scheduled` | 不是终态，只是安排了下次执行 |
| `api_key_masked` vs `has_api_key` | 前者是掩码，后者是布尔 |
| 草稿 ≠ 正式落库 | 副作用需过人工闸门 |
| 注册了工具 ≠ 能执行 | 网关无适配器照样拒 |
| 检查点恢复 ≠ 新建任务 | 必须同一 `thread_id` |
| 节点名 ≠ 函数名 | 条件边返回字符串必须精确匹配已注册节点名 |
| `resume_queued` ≠ 已落库 | 需轮询到 completed |
| Outbox 写入 ≠ 已发布 | 投递由调度器/Beat 完成 |

## 五、高频追问的深度要点

1. **为什么单 Agent 不可靠**：幻觉、无真实数据/工具、不可审计 → 多 Agent + 工具白名单 + 风险分级 + 人工闸门。
2. **人工闸门为何不能只靠 Prompt**：Prompt 可被绕过/漂移，需要代码级的 `interrupt()` + 审批状态机 + 角色权限。
3. **预算「调用前截断」而非事后统计**：避免超支后才熔断，`remaining_model_tokens` 返回 `min(申请,剩余)`。
4. **`extra="forbid"` 的意义**：LLM 输出漂移时，严格拒绝比静默忽略多余字段更安全、更早暴露问题。
5. **幂等键的生成与查询时机**：`tool:{agent}:{tool}`、`agent-run:{run_id}:{suffix}`，失败回滚后另开会话记失败。
6. **Celery 加 `@task` 不会自动异步**：必须 `.delay()`，且返回任务编号非结果。
7. **LangGraph 恢复必须同一 `thread_id`**：变了找不到 checkpoint，等于新建任务。
8. **`interrupt()` 前不写业务代码**：checkpoint 恢复会重复执行，产生副作用。
9. **`selectinload` 防 N+1**：路由层预加载关联，避免循环查询。
10. **`Decimal` 转字符串再 JSON**：避免精度丢失，`Numeric(10,2)`。
11. **fencing 五道校验 + `_sync` 双重确认 + 行锁**：三管齐下阻止旧 Worker 写终态。
12. **`skip_locked` 的作用**：多实例并发扫 Outbox 时，已锁定的行被跳过，避免重复消费。
